# PAO facts research handover

You are a meticulous research model. Your job is to find **real, checkable
factual connections** between each number 00–99 and its assigned **Person**,
**Action**, and **Object** in the PAO number-memory system. You will search the
web, verify every claim against a source you actually opened, and write the
results to one Markdown file in the exact format below.

This is a research task, not a creative-writing task. A blank cell is acceptable.
A fabricated connection is not.

> **Critical: three roles, not one.**
> A previous pass returned mostly Person notes and almost no Action or Object
> notes. That is a failure mode, not an acceptable result. Finding a Person hook
> does **not** complete a number. Every number must be researched three times —
> once for the Person, once for the Action, and once for the Object — with
> independent searches and independent sources. Do not stop at the Person.
>
> It is fine to conclude that an Action or Object has no real hook. It is not
> fine to skip the search, or to invent a weak link because the Person note was
> easy.

---

## 1. What PAO is

PAO maps every two-digit number to three words:

- **P** — a Person
- **A** — an Action
- **O** — an Object

For example, 23 is **Jordan / skating / xylophone**. The app shows a short note
under each role explaining why that word could belong to that number.

The assignments were chosen as mnemonic imagery. **Many of them have no historical
or factual connection to their number.** That is expected. Your job is to find the
connections that genuinely exist, not to justify every word. If a role has no real
hook, record it as “no verified hook” and explain what you searched.

**Do not infer or invent the original author’s intent.** You are testing whether a
specific, documented fact links the word to the number.

## 3. What counts as a valid connection

A valid connection is **specific, documented, and checkable**. The number must
appear explicitly, or follow by exact arithmetic from documented dates or counts.

Acceptable kinds of hook include:

| Kind | Example shape |
|------|---------------|
| Documented age at a dated event | “turned 34 eleven days before the album shipped” |
| Birth or death date/year | “born 16 April 1889” |
| Jersey or shirt number | “wore 23 for the Bulls” |
| Atomic number | “iron is element 26” |
| Exact count | “19 successful title defenses” |
| Exact letter/character count | “seven letters in Presley” — count it yourself and label it wordplay |
| Publication/film/album/episode title | “directed the 1932 film *Number Seventeen*” |
| Ordinal / numbered work | “BWV 40”, “Op. 41”, “OV-099” |
| Address, route, designation | “33 Union Square West” |
| Award/list rank | “ranked #81” |
| Record or measurement | “flight lasted 1 hour 48 minutes” |
| Fictional first appearance | “first appeared in *Detective Comics* #27” |
| Product/model name | “Nintendo 64” |

**Unacceptable:**

- “Associated with”, “famous for”, “known for”, “connected to” with no number.
- A number that only appears in a birthday year after cherry-picking a different
  event, when the age link is not the documented reason.
- Approximate counts presented as exact (“about 30” written as “30”).
- Numerology, gematria, astrology, “sacred number” speculation.
- Letter counts that are wrong, or that quietly include or exclude spaces to fit.
- Reusing the same fact for multiple roles unless each role has a distinct,
  documented link.
- A fact that is true of the person but unrelated to the number.
- Anything you cannot trace to a URL you actually opened and read.

**If the only link is a stretch, reject it.** Put it in the rejected table with a
one-line reason. Do not put it in the main table.

## 4. Research process — think hard and search properly

Work in batches of ten numbers (00–09, 10–19, …). For each number, research the
Person, the Action, and the Object **independently**, and log your queries as you
go.

**A number is finished only when all three roles have an outcome:** a kept note, a
rejected candidate, or a documented “no verified hook.” A Person note alone does
not finish a number.

### 4.1 Search aggressively — all three roles

Do not rely on memory. Use web search for every cell. Run **at least three
distinct queries per role** before concluding there is no hook.

**Person**

- `"<person>" "<n>"`
- `"<person>" age <n>`
- `"<person>" born <date>`
- `"<person>" jersey number`
- `"<person>" <n>th`
- `"<person>" <year>` where the year ends in the number
- `"<person>" <n> <record/album/film/role>`
- Official biography, Britannica, museum, league, government, publisher

**Action — expect this to be harder, so search harder**

Actions rarely have a Wikipedia “age” or “jersey number.” Look for numbered
records, rules, techniques, and titled works:

- `"<n>" "<action>"`
- `"<n> <action>"` and `"<action> <n>"`
- `"<n> <action> record"` / `"<action> world record <n>"`
- `"<n> ways to <action>"` / `"<action> in <n> seconds"`
- `"rule <n>" "<action>"`, `"section <n>" "<action>"`, `"article <n>" "<action>"`
- `"the <n> <action>"` — a named technique, drill, or operation
- sports: `"<n> <action> attempts"`, `"<n> <action> titles"`, `"<n>th <action>"`
- titles: `"<n> <action>" film`, `"<n> <action>" book`, `"<n> <action>" song`
- safety, standards, and government pages that number a procedure
- exact letter count of the action word — only as a last resort, only if exact,
  and label it `wordplay:`

**Object — search products, counts, titles, and designations**

Objects often have the strongest non-Person hooks. Look for:

- `"<n>" "<object>"`
- `"<object>" model <n>` and `"<object> <n>"`
- `"<n>-<object>"` — a compound name or measurement
- titled works containing the number and the object
- exact counts: components, contents, sizes, capacities, or pack quantities
- product model numbers, serial numbers, and official designations
- addresses, rooms, routes, patents, and catalog numbers
- museum records, archives, standards documents, and official manuals
- unit definitions and measurements involving the object

Also try the reverse: search the number plus a likely fact type, e.g.
`"99" "OV-099"`, `"40" "BWV 40"`, `"52" "52 weeks"`.

**Never reuse the Person evidence for the Action or Object.** Each role needs its
own source and its own number link.

### 4.2 Open the source

A search-result snippet is not a source. Open the URL and read the relevant
passage. Record:

- the exact claim the source makes,
- the sentence or table row that supports it,
- whether the number appears explicitly or is derived,
- the publication date if the page is time-sensitive.

If the page is paywalled, 403, or unreadable, find another accessible source. If
you cannot, drop the row. Never cite a URL you did not open.

### 4.3 Do the arithmetic

For ages and intervals, write out the calculation in the evidence field:

> born 6 February 1945; event on 1983-05-11 → age 38.

For counts, count the items. For letter counts, count the letters yourself and
state whether spaces and hyphens are included.

### 4.4 Source hierarchy

1. **Primary / official** — NASA, national archives, official team or league,
   museum, publisher, government, standards body, official product page.
2. **Reputable secondary** — Britannica, major newspaper, established biography,
   university page.
3. **Wikipedia** — acceptable only for uncontroversial facts when nothing better
   is available; mark the row `medium` at best.
4. **Fan wikis, content farms, SEO listicles, unsourced blogs** — not acceptable
   as the only source. If used at all, they must be corroborated.

If two sources disagree, prefer the primary source and note the conflict.

### 4.5 Be honest about coverage

You are aiming for as many real connections as possible across all 300 cells.
But **do not fill cells for the sake of coverage**. A role with no hook must be
recorded in the “No verified hook” section. That section is proof of work, not a
failure.

Person, Action, and Object carry **equal weight**. A result with 80 Person notes
and 3 Action/Object notes is not a complete pass — it means the Action and Object
searches were not done properly. Before you finish, compare the counts by role.
If Action or Object is far behind, go back and search those cells again with new
queries. Do not fabricate notes to balance the numbers.

A partial prior pass exists in `docs/pao-notes.md` if it is available. Treat it
only as a list of leads. Re-verify every claim independently. Do not copy a note
just because it is already there. That earlier pass skewed heavily toward Persons;
do not inherit its gaps.

## 5. Note style

The `note` field is what the app will display. Keep it:

- **90 characters or fewer**, including spaces.
- **lowercase**, except proper nouns if unavoidable.
- **no trailing period**.
- terse and declarative.
- one fact only.
- no “source:” text, no markdown links, no quotation marks around the whole note.
- no vague words: “famous”, “associated”, “linked”, “known for”.
- include the number explicitly whenever possible.

Examples of acceptable notes:

- `jordan wore 23 for the chicago bulls`
- `socrates was executed in 399 bce`
- `challenger (ov-099) broke apart 73 seconds after launch`
- `iron's atomic number is 26`
- `wordplay: indiana=7 letters, jones=5, giving 75`

If the note is a letter-count wordplay note, start it with `wordplay:` so the
app can style it differently.

## 6. Output file

Write exactly one file:

`docs/pao-facts-v3.md`

Do not edit any other file. Do not change the app source code.

Use this structure:

````markdown
# PAO facts v3 — 00–99

## Summary

- Cells accounted for: 300 / 300
- Notes kept: <total> (P <n> / A <n> / O <n>; strong <n>, medium <n>)
- Rejected as weak: <total> (P <n> / A <n> / O <n>)
- No verified hook: <total> (P <n> / A <n> / O <n>)
- Numbers with no notes at all: <comma-separated list or “none”>

## Method

<3–6 sentences: which source types you used, how you checked ages and counts,
and what you deliberately rejected.>

## Facts

| n | role | word | note | source | evidence | confidence |
|---|------|------|------|--------|----------|------------|
| 00 | P | James Bond | ... | https://... | ... | strong |

## Rejected as weak

| n | role | word | candidate | source | why rejected |
|---|------|------|-----------|--------|--------------|

## No verified hook

| n | role | word | searches tried | why nothing qualified |
|---|------|------|----------------|-----------------------|

## Coverage ledger

Every number must appear below, with one outcome per role. Allowed values are
`note`, `rejected`, or `none`. This table is mandatory: it proves that no role was
skipped. It must contain exactly 100 rows (00–99), and its totals must match the
Summary. Never collapse two roles into one cell.

| n | P | A | O |
|---|---|---|---|
| 00 | note | none | rejected |
| 01 | note | rejected | none |

## Machine-readable data

```json
[
  {
    "n": 0,
    "role": "P",
    "word": "James Bond",
    "note": "...",
    "sources": ["https://..."],
    "evidence": "...",
    "confidence": "strong",
    "kind": "designation"
  }
]
```
````

### 6.1 Table rules

- `n` is always two digits in the Markdown table (`00`, `07`, `99`).
- `role` is exactly `P`, `A`, or `O`.
- `word` is the exact assignment from the table in section 2.
- `source` is one plain URL. If you need a second source, put it in `evidence`
  after the quote as `also: https://...`.
- `evidence` is a short quote or precise paraphrase that contains the number or
  the exact dates needed for the calculation. Escape any `|` as `\|`.
- `confidence` is `strong` or `medium` in the main table. Anything weaker goes
  to the rejected table.
- Every row must be unique by `(n, role)`.

### 6.2 JSON rules

The final fenced JSON block is the canonical data for integration. It must be
valid JSON and must parse with `JSON.parse`. No comments, no trailing commas, no
ellipses.

Each object has:

| field | type | meaning |
|-------|------|---------|
| `n` | integer 0–99 | the number |
| `role` | `"P"`, `"A"`, or `"O"` | the role |
| `word` | string | exact assignment |
| `note` | string | app-ready note, ≤90 chars, lowercase, no period |
| `sources` | string[] | 1–2 opened URLs |
| `evidence` | string | quote or precise paraphrase supporting the claim |
| `confidence` | `"strong"` or `"medium"` | same as the table |
| `kind` | string | one of: `age`, `date`, `jersey`, `atomic`, `count`, `letters`, `title`, `ordinal`, `address`, `rank`, `record`, `appearance`, `product`, `designation`, `other` |

The JSON must contain exactly the same rows as the main table — no extras, no
omissions. Count them and confirm the counts match before you finish.

## 7. Self-audit before you finish

Run this checklist and fix anything that fails:

1. **Coverage:** every one of the 300 `(n, role)` cells appears exactly once —
   either in the main table/JSON, the rejected table, or the no-hook table.
2. **Ledger:** the coverage ledger has exactly 100 rows, every cell is filled
   with `note`, `rejected`, or `none`, and the totals match the Summary.
3. **Three-role discipline:** no number was closed after only a Person search.
   Every number has an independent outcome for P, A, and O.
4. **Role balance:** count kept notes by role. If Action or Object is far behind
   Person, you have probably repeated the previous pass's failure. Go back and
   run fresh queries for the weakest role. Do not fabricate notes to close the
   gap; keep searching, then record honest no-hooks.
5. **Query depth:** every `none` or `rejected` row lists at least three distinct
   searches that were actually tried.
6. **URLs:** every source URL was opened and supports the claim. No bare search
   snippets, no guessed URLs, no dead links.
7. **Arithmetic:** every age and interval is recalculated from the stated dates.
8. **Counts:** every count is exact; approximate counts are either labeled or
   rejected.
9. **Letter counts:** recounted by hand; spaces/hyphens policy stated.
10. **Notes:** all ≤90 characters, lowercase, no trailing period, no vague words.
11. **No duplicates:** no `(n, role)` repeats; the same fact is not stretched
    across roles.
12. **No invented numbers:** the number in each note is either in the source or
    derived by explicit arithmetic.
13. **JSON:** parses cleanly; matches the table; counts match the summary.
14. **Honesty:** weak or tangential links are in the rejected table, not the
    main table.

If a row fails any check and you cannot fix it, move it to rejected or no-hook.
